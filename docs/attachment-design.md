# 附件引用与模型输入设计

## 1. 设计目标

LUMORA 的附件遵守“内容只保留一份”原则：数据库只保存引用关系和展示元数据，
不保存文件二进制、Base64，也不建立应用自己的托管附件副本。

| 输入来源 | 内容保存位置 | LUMORA 持久化内容 |
| --- | --- | --- |
| 资源管理器选择、拖入或粘贴的文件 | 用户原始绝对路径 | 路径、名称、MIME、大小、类别 |
| 剪贴板中的纯图片数据 | 操作系统临时目录中的单个临时文件 | 临时路径和同一组元数据 |

因此，本地原文件被移动或删除后，历史消息仍能显示附件名称，但不再承诺预览或发送；
剪贴板图片随操作系统临时目录清理而失效。这是预期行为，不会静默复制第二份内容。

## 2. 数据流

```text
文件选择 / 拖放 / 粘贴
  ├─ 能取得本地绝对路径 → 直接建立 LOCAL_FILE 引用
  └─ 只有图片字节        → 写入系统 Temp → 建立 CLIPBOARD_TEMP 引用
             ↓
Renderer 消息与问题队列
             ↓
Java Core 的 attachments_json（仅元数据）
             ↓
Python Provider 组装请求时临时读取路径
             ↓
图片进入供应商多模态消息；PDF 进入本地只读工具
```

附件内容只在模型请求组装或工具执行阶段短暂进入内存。图片转换为供应商要求的图像块；
文本文件转换为带文件名边界的文本块。PDF 不再依赖供应商是否支持 `document` / `input_file`，
而是向模型提供 `attachmentId`，由 `read_pdf` / `search_pdf` 读取。模型请求完成后不会把这些
字节或解析结果写回会话数据库。

## 3. PDF 工具读取

- `read_pdf` 默认读取 5 页，单次最多 10 页，并返回总页数与 `nextStartPage`。
- `search_pdf` 默认扫描 100 页，单次最多 200 页，并返回命中页码与上下文。
- 工具参数只接受当前 Run 中出现过的 `attachmentId`，模型不能借此读取其他磁盘路径。
- PDF 即使位于工作区外也不需要放宽工作区沙箱；附件 ID 只映射到用户已经上传的那一个路径。
- 同一 PDF 的并发读取共享文件读锁；读取过程中若文件发生变化，本次结果作废并要求重试。
- 当前版本读取 PDF 文本层。扫描件会返回 `ocrRequired=true`，不伪造识别结果；OCR/视觉代理
  属于后续独立能力。

## 4. 桌面端边界

- Renderer 不能直接访问 Node.js 文件系统；Preload 只暴露附件准备和只读图片预览接口。
- Electron Main 负责校验路径、类型和大小，并在系统临时目录物化纯剪贴板图片。
- 本地文件通过 Electron 的 `webUtils.getPathForFile` 取得真实路径，不创建历史附件目录。
- 图片预览按需从路径读取，只生成内存中的 Data URL；预览数据不进入消息协议或数据库。
- 当前每条消息最多 10 个附件，图片不超过 20 MB，其他文件不超过 25 MB。

## 5. 会话、队列与恢复

`conversation_message`、`conversation_run` 和 `conversation_input` 均只保存
`attachments_json`。这样附件会随问题气泡显示，也能随下一轮问题队列和重启后的 Run
恢复继续传递，不依赖 Renderer 内存。

当前 Steer 是正在运行轮次的轻量文本引导协议，不在半轮请求中注入附件。因此，带附件的
问题只能作为完整的下一轮输入排队；界面会禁用该项的“调整方向”，避免用户误以为附件已
进入当前模型上下文。

## 6. 失效与安全语义

- 发送前若路径已经失效，Provider 不伪造副本，而是向模型加入“附件不可用”的明确文本。
- 历史 UI 保留文件名和类型；图片缩略图读取失败时降级为附件占位图。
- 系统临时图片采用 `lumora-clipboard-*` 名称，由操作系统临时目录生命周期负责清理。
- 路径必须为绝对路径，附件 DTO 在 Electron、Java 和 Python 三层均进行数量与字段校验。

这一方案优化的是长期磁盘占用和行为可解释性；它不提供附件归档或跨设备迁移保证。若未来
需要可移植导出，应由用户显式选择“连同附件打包”，而不是在日常会话中默认保存第二份。
